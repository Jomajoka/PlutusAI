# PlutusAI — Build Progress

Tracks checkpoint status for the build. See each checkpoint's section for what was built, verified, and any decisions/gotchas worth remembering.

## Project-wide scoping decisions (set 2026-10-27, before Checkpoint 2)
These came out of a planning discussion about avoiding "just an LLM wrapper that visualizes data" and keeping free-tier-LLM constraints realistic:
- **No vision/multimodal, no OCR.** PDF ingestion is text-layer extraction only (`pdfplumber`/`PyMuPDF`). Scanned/image-only PDFs are out of scope. This also means free-tier text-only LLMs are sufficient — no need for a multimodal model anywhere in the pipeline.
- **Report scope narrowed to standard financial reports** (quarterly/annual filings — e.g. SEC EDGAR 10-K/10-Q, company IR PDFs) rather than arbitrary business documents. These have predictable terminology/structure, which is what makes the keyword/numeric-density page-filtering heuristic viable.
- **CSV/Excel ingestion dropped entirely.** Doesn't match the real use case (small businesses have data in document/report form, not clean spreadsheets) and would have been a third, separate ingestion path for no real benefit. **Text and PDF input are now the only (and core) ingestion modes** — see Checkpoint 2 below. This is a deliberate strength of the system, not just a fallback: the pitch is that it can go through a messy real report and pull out only what's substantial, rather than requiring the user to pre-structure their data.
- **Deterministic-first extraction — the LLM never invents numbers, it only organizes already-extracted ones.** Pipeline, in order:
  1. **Local, deterministic, no LLM, free:** regex/pattern matching over the raw text to pull out candidate (label, value, surrounding context) triples near known financial keywords (e.g. "Revenue: $X", "Units sold: X", currency-adjacent numbers). This is the actual number-extraction step, and it's unit-testable on its own.
  2. **(PDF only) Page filtering first:** before step 1, score pages by keyword hits / numeric density / TOC parsing to shortlist ~10-20 of a 100-200 page report, so step 1 only runs over likely-relevant pages. Not needed for pasted text since it's already short.
  3. **LLM, structuring only:** given the deterministically-extracted candidates (not the raw document), the LLM's job is narrower and safer than "read this and find the numbers" — it maps each candidate to the canonical schema (which field, which product, which period) and resolves terminology (e.g. "turnover"/"sales" → `revenue`, "COGS"/"direct costs" → `cost`). It cannot hallucinate a number that doesn't exist, since it never sees free text to begin with, only pre-extracted candidates.
  4. **Deterministic validation:** the mapped values are still cross-checked against the original extracted candidates (not re-derived from scratch) as a final consistency check.
  5. **User-editable confirmation table** before saving — catches anything genuinely ambiguous or missed.
- **Schema stays rigid-but-minimal, not universal, with explicit fallbacks for variation between businesses:**
  - Canonical schema covers the lowest common denominator the calc engine actually needs (period, revenue, units, cost, product) — not an attempt to model every business's accounting style.
  - Fields are **nullable, not required** — e.g. a business with no per-product breakdown just has a single generic product entry rather than failing to fit.
  - The LLM's structuring step (1.3 above) explicitly includes terminology mapping to the fixed schema field names, rather than the schema trying to grow to match each business's vocabulary.
  - Anything that doesn't map cleanly surfaces in the confirmation table rather than being silently forced into the wrong field.
  - This is honestly scoped as "handles the common case well," not "handles arbitrary business data" — consistent with the proof-of-concept accuracy bar.
- **Demo strategy:** for the live demo, prepare a curated PDF and/or pasted-text sample ourselves that's known to extract well, rather than relying on a random real-world document live on stage. Real messy documents are for showing robustness during development/testing, not for the actual demo moment.
- **Prediction accuracy bar: proof-of-concept, not production-grade.** Naive/simplified assumptions are acceptable and should be shown explicitly (e.g. "elasticity assumed/estimated as X") rather than hidden — honest-naive beats hidden-naive.
- **No training a model on external business datasets.** Rejected due to data availability/overfitting risk vs. a college-project timeline. Worth mentioning as considered-but-deferred future work in the writeup. The per-business elasticity estimation (fit from that business's own historical quarters, see Checkpoint 4 depth additions below) is the scoped-down version of the same idea and is still planned.
- **LLM access is free-tier only, by firm user decision — no paid models.** Mitigations: fallback chain of 2+ free models per task (try A, retry B on failure/timeout) rather than relying on one; deterministic validation + human confirmation table catch quality gaps regardless of model strength; model names kept config-driven (not hardcoded) since free-tier lineups change over time.

## Visualization is a first-class concern, not an afterthought
Agreed during planning: the calc-engine depth additions below are only as impressive as their visualization. Principles for Checkpoint 3 (dashboard) and Checkpoint 5 (scenario results) onward:
- Each feature gets a visual form suited to it, not a generic bar chart: elasticity/sweep optimizer → curve with optimum point highlighted; backtest → predicted-vs-actual comparison view; dashboard → trend (revenue over time) + composition (product mix) charts.
- One consistent color system, chart style, and interaction pattern (tooltips/legends) across the whole app, so it reads as one polished product.
- Recharts is the library; the quality bar comes from deliberate design (color/layout/emphasis) applied when we actually build these, not default chart styling.

## Checkpoint 4 depth additions (to avoid being "just an LLM wrapper")
Agreed during planning, to be built as part of Checkpoint 4 (deterministic calc engine), not Checkpoint 5:
1. **Elasticity estimated from the business's own historical data** (simple regression across their own periods) with fallback to an industry-default constant when there isn't enough historical variation — real statistics, not an LLM guess.
2. **Scenario sweep/optimizer**: sweep a lever (e.g. price) across a range and plot the resulting profit curve, marking the optimum — reframes the product from "answer one question" to "recommend the best move."
3. **Back-test validation**: where a product's history includes a real price/cost change, run the model as if it only knew data before that point and compare its prediction to what actually happened — genuine model validation, strong demo moment.
4. (Lower priority) Side-by-side comparison of multiple scenarios in one view.

## Checkpoint 2 — Text + PDF ingestion ✅ Done
This is the core ingestion checkpoint (CSV/Excel was dropped — see scoping decisions above) and the system's main differentiator: going through messy real documents and extracting only what's substantial, rather than requiring pre-structured input.
- Built: `products`/`financial_records`/`business_notes` tables + RLS; deterministic candidate extraction (regex/keyword, no LLM, 14 unit tests); PDF page scoring/selection (keyword+number density, no LLM, 6 unit tests, proven against a real generated PDF); LLM structuring with deterministic post-hoc validation against the original candidates (8 unit tests, including the core guarantee that an altered/invented value is rejected, not trusted); record grouping into per-product/period rows (6 unit tests); `/ingest/text/preview`, `/ingest/pdf/preview`, `/ingest/text/confirm` endpoints; frontend ingestion UI (paste text/upload PDF, editable review table with verified/unverified badges, source-line traceability, notes section).
- Decisions:
  - LLM client made provider-agnostic (`LLM_API_KEY`/`LLM_BASE_URL`/`LLM_STRUCTURING_MODELS`, any OpenAI-compatible endpoint) after OpenRouter's free-tier model (`google/gemma-4-26b-a4b-it:free`) kept hitting shared-pool rate limits (429s) during testing. Switched to **Groq** (`https://api.groq.com/openai/v1/chat/completions`, model `qwen/qwen3.8-27b`), which has a generous free tier and worked reliably.
  - Candidates carry a `context_text` field (last 3 non-blank preceding lines) alongside the matched line. Without this, a real multi-product test showed the LLM correctly refusing to guess product/period (defaulting everything to "General"/"Unknown") since it only saw an isolated line like "Total revenue: $500,000" with no heading above it. Adding context_text fixed this — verified against real multi-product/multi-period text through Groq.
- Verified: full pipeline (extraction → Groq structuring → validation → grouping) tested directly in Python against realistic multi-product text, then end-to-end through the real UI on the deployed Vercel+Render+Supabase stack — pasted text saved correctly into `financial_records`/`products` under the right business.
- Gotcha: a locally running `uvicorn --reload` process does **not** pick up `.env` changes — `--reload` only watches code files, not env vars, since `python-dotenv` loads once at process start. Must fully restart the process after editing `.env`, not just save-and-let-it-reload.

## Checkpoint 4 — Deterministic calc engine ✅ Done (core logic; not yet wired to the UI)
- Built, all pure Python, no LLM, 20 unit tests total:
  - `simulate_price_change()` / `simulate_sourcing_change()` (`pricing.py`) — constant-elasticity demand response, clamps units sold at zero, hand-computed fixtures.
  - `estimate_elasticity()` (`elasticity.py`) — fits elasticity via log-log regression across a product's own historical periods. Key realization: we don't store price per period directly, but `revenue / units_sold` per `financial_records` row already gives an *implied* price per period, so no schema change was needed. Falls back to a documented default constant (`-1.5`) when there's fewer than 3 periods or no real price variation to regress against — surfaced via `is_estimated`, never hidden.
  - `sweep_price_change()` (`sweep.py`) — sweeps a price-change range and returns every point plus the profit-maximizing one. Verified against a hand-derived parabola optimum.
  - `backtest()` (`backtest.py`) — holds out the latest period, estimates elasticity from everything before it, predicts the held-out period's units/revenue, and compares to what actually happened. Verified both with an exact-match fixture (held-out period follows the same power law as its history) and a thin-history fallback case.
- Not yet done: no API endpoint or UI exposes any of this yet — these get wired in at Checkpoint 5, where the LLM parses a user's NL scenario question into params and calls these same tested functions.

## Checkpoint 5 — Scenario query parsing + narration (LLM wired in) ✅ Done
- Built (`app/scenario/`): `parsing.py` (LLM → `{lever, product_name, magnitude}` only, validated), `resolution.py` (deterministic product-name matching: exact, then fuzzy via stdlib `difflib` with a confidence-lead check so a near-tie asks for clarification instead of guessing — 6 unit tests), `runner.py` (decides single-vs-sweep, clamps nonsensical magnitudes to `[-0.95, 5.0]`, calls the Checkpoint 4 functions — 17 unit tests), `narration.py` (LLM narrates a small pre-computed summary, never raw data; failure is non-fatal — numbers still return without narration). `/scenario/query` endpoint wires it all together. 85 backend tests total. Frontend `/scenario` page: NL input, before/after bar chart (emphasis form — "after" colored by profit direction, "before" de-emphasized gray) for single-point results, profit-curve-with-optimum-marked line chart for sweeps, clarification messages surfaced directly (not silently guessed past).
- Verified live against Groq for all three branches: price change with a given magnitude (single simulation), an open-ended "what's the best price" question (correctly triggered a sweep, no guessed number), a sourcing-cost question (correctly extracted the lever and magnitude), and a query naming a nonexistent product (model correctly returned a null product name rather than hallucinating a match, leading to a clarification response).
- Plan (reference): OpenRouter, per-task model routing (strong model for parsing, cheap model for narration). NL query → structured params → calls the tested calc function → narrates the already-computed result. (Implemented with Groq/single-model-chain rather than OpenRouter — see Checkpoint 2 decisions above for why.)
- **Full pipeline, worked out in planning (example: "what if I increase the price of product X"):**
  1. LLM parses the NL query into structured params only: `{ lever, product_name, magnitude }`. It is given the business's actual product name list as grounding context, so it matches against real names instead of inventing one. The LLM never picks a chart or computes a number — strictly query → params.
  2. Backend resolves `product_name` against the real `products` table itself (exact match, then fuzzy match) — not the LLM's job. If no match or an ambiguous match, return a clarifying response to the frontend (e.g. "did you mean 'Phone Case'?") instead of guessing.
  3. **Missing magnitude is a signal, not an error**: if the user didn't specify an amount ("increase the price" with no number), default to running the Checkpoint 4 sweep/optimizer across a range for that lever, instead of guessing a percentage. If a magnitude was given ("by 10%"), run the single before/after simulation instead. Chosen deterministically by whether `magnitude` parsed as null.
  4. Calc engine runs with basic guardrails (reject/clamp nonsensical magnitudes, e.g. -500%).
  5. **Chart template is selected by which function ran / the output's shape, never decided by the LLM**: sweep output → curve-with-optimum-marked template; single-point output → before/after bars. This mirrors the dashboard's deterministic chart-template approach from Checkpoint 3 planning.
  6. LLM narrates last, off a small summary of the result (e.g. current point + optimum point), not the raw array — and the narration should keep the "this is a simplified/naive estimate" framing visible, per the proof-of-concept accuracy bar.
- **Division of labor, as a standing principle**: the LLM decides *what to compute* (which function, with what params); fixed code decides *what to chart* and *how to validate/resolve* inputs. The LLM is never the source of truth for data matching, chart selection, or the numbers themselves.

## Bug fix: new products on a second ingestion were dumped into "General"
Found during manual testing (pasting a 3rd, brand-new product into a business that already had 2 products saved from a prior ingestion). The structuring system prompt told the LLM to assign each candidate's product "using the provided list of known product names, or 'General' if none fit" -- worded ambiguously enough that once `known_product_names` was non-empty, the model read it as a closed set and forced a genuinely new product (clearly named in `context_lines`, e.g. a "Specialty Soda" heading) into "General" rather than using the new name. This didn't show up in Checkpoint 2 testing because that was always a *first* ingestion with an empty known-products list, where the model had no choice but to invent names from context.
- Fix: reworded `app/llm/structuring.py`'s system prompt to explicitly state that `known_product_names` is prior products, not an allowed-list, and that a new product name clearly given in `context_lines` should be used as-is -- "General" is only for when context genuinely gives no product name at all.
- Verified live against Groq: reproduced the exact failing conditions (known_product_names=["Pastry Box", "Latte"], candidates for a new "Specialty Soda") -- all 6 candidates now correctly map to "Specialty Soda" instead of "General". 117 backend tests still pass (no test changes needed; this was a prompt-wording fix, not a logic change).

## Reduce LLM usage during ingestion ✅ Done
Prompted by the Specialty Soda investigation: ingestion was already down to exactly one LLM call per preview (confirm makes zero), so the real fix there was the prompt-wording bug above, not call count. Still, a genuine further reduction was possible: resolve the easy, unambiguous candidates deterministically and only send the LLM what actually needs judgment.
- **`app/extraction/candidates.py`**: `Candidate` now also carries `nearest_period_text` -- the most recent line anywhere earlier in the whole document that parses as a real period (via `periods.parse_period`), tracked as `extract_candidates()` scans top-to-bottom. This is purely syntactic (no business-specific knowledge needed), so tracking it unboundedly is just as safe as the existing fixed-size context window, only not limited by it -- important because a period heading is often stated once and applies to several products listed below it (exactly our Golden Cup Cafe layout), which a fixed lookback window alone would miss for the 2nd+ product. Context window bumped 3->4 lines too, so a 3rd field under a typical 2-line (period + product) heading block still has the product heading in view.
- **`app/extraction/fast_path.py`** (new): `resolve_deterministic(candidates, known_product_names)` resolves a candidate with zero LLM involvement only when BOTH an exact (case-insensitive) match to an already-known product name is found in its local context AND `nearest_period_text` is set -- i.e. only when there's a real, already-known product and a real period, never a guess. Anything else (a brand-new product, no period seen yet, genuine ambiguity) falls through to the LLM structuring step unchanged, which remains the safety net. A pure extension of the project's deterministic-first philosophy, not a new risk.
- `_preview_from_text()` in `app/api/ingestion.py` now runs the fast path first and only calls the LLM on leftover candidates -- skipping the LLM call **entirely** if everything resolved deterministically.
- Verified against the real Golden Cup Cafe dataset (2 known products, 1 new product mixed in): 12 of 15 candidates resolved with zero LLM calls; only the 3 candidates for the genuinely new product were sent to the LLM. For a business with no new products in a given paste, this drops the LLM call count for that preview to zero.
- Verified: 126 backend tests pass (10 new: 3 in `test_candidates.py` for `nearest_period_text` tracking, 6 in `test_fast_path.py`, plus the context-window bump required no other test changes).

## Bug fix: revenue-over-time chart sorted periods lexically, not chronologically
Found during manual testing (Specialty Soda's line looked "broken" on the dashboard despite being correctly classified now). Root cause: `build_dashboard_summary()`'s `revenue_trend` was sorted with plain `sorted(...)` on the `(period, product_name)` tuple -- a plain string sort of "Q1 2023".."Q4 2024" groups by quarter digit first and year second ("Q1 2023", "Q1 2024", "Q2 2023", ...), not true chronological order. This didn't look broken for Latte/Pastry Box, which have a data point in every quarter (a value at every x-axis position still draws a continuous line even in the wrong order). Specialty Soda only has data in Q3 2024 and Q4 2024 -- under the scrambled order, "Q4 2023" (where it has no data) landed *between* those two points, creating a real gap in its line, even though Q3 2024 and Q4 2024 are directly adjacent in actual time.
- Fix: `app/dashboard/aggregation.py` now sorts `revenue_trend` by a real chronological key, reusing `app/calc_engine/periods.py` (`parse_period` + `period_date_range`) to turn each period into a real orderable date. Periods that don't parse (free-text, no year) fall back to sorting after every real one, by their own text -- never crashes, never guesses a date.
- Verified: 127 backend tests pass (1 new regression test asserting "Q1 2023", "Q2 2023", "Q1 2024" sort in that chronological order, not lexical).

## Bug fix: sourcing/price scenarios silently used cost = $0
Found during manual testing ("what if my supplier cost for Latte drops 20%?" reported zero profit change -- should have increased). Root cause: `products.unit_cost` is never actually populated anywhere in the ingestion pipeline -- only `unit_price` is tracked at the product level (`app/extraction/grouping.py` only builds a `unit_prices` map, no equivalent for cost); real cost only ever lives per-period in `financial_records.cost_breakdown`. `run_scenario()`'s baseline used `product.get("unit_cost") or 0.0`, which was *always* 0.0 in practice -- every sourcing-change scenario, and every price-change profit number, had been silently computed with zero cost this whole time.
- Fix: `app/scenario/runner.py`'s `_latest_baseline()` now also derives `cost_per_unit` from the most recent period's `cost_breakdown.total_cost / units_sold` -- the same "implied value from real per-period data" pattern already used for price and elasticity (see Checkpoint 4 notes) -- falling back to `product.unit_cost` only if no record has usable cost data, and to `0.0` only as an absolute last resort.
- Caught and fixed a second bug in the same function while rewriting it: the "most recent period" lookup sorted periods as plain strings (`sorted(..., key=lambda r: r.get("period"))`), which for a multi-year product groups by quarter digit first and year second -- same bug class as the dashboard chart fix above, just in a different file. Now reuses `app/calc_engine/periods.py` for a real chronological sort.
- Verified against the exact reported case: Latte, 20% cheaper sourcing, Q4 2024 baseline (cost $1.50/unit, 1400 units) -- profit now correctly rises from $4,200 to $4,620 (+$420), not $0.
- Verified: 129 backend tests pass (2 new regression tests: deriving cost from `financial_records` when `product.unit_cost` is null, and picking the true latest period across years rather than the lexically "largest" one).

## Bug fixes found during a systematic what-if eye-test pass
Before trusting the suggested test questions, actually ran them against the real Golden Cup Cafe data rather than just reading the code. Found two more real issues and one false alarm:
- **Positive elasticity = a backwards prediction.** Latte's history has units_sold varying mostly from seasonality at a near-constant price, plus exactly one real price change -- enough to confound the regression into a *positive* slope (implying "raising price increases demand," impossible for a normal good). `estimate_elasticity()` now explicitly rejects a positive slope and falls back to `DEFAULT_ELASTICITY` with `is_estimated=False`, same as any other "couldn't fit a real line" case -- never hands back a confidently-wrong, backwards number. 1 new regression test.
- **The same lexical-period-sort bug (fixed twice already, in the chart and in the scenario baseline) existed a third time**, in `app/dashboard/validation.py`'s backtest grouping -- it happened to coincidence into the right answer for our specific demo data, but would silently misidentify "latest period" for a dataset where the max quarter number and max year don't line up (e.g. anything crossing into a new year's Q1 while last year's Q4 is still in the data). Extracted one shared `period_sort_key()` into `app/calc_engine/periods.py` and pointed `aggregation.py`, `runner.py`, and `validation.py` at it instead of three separate (and now provably drifting) copies. Also fixed `validation.py` passing `product.get("unit_cost")` (always 0, see the bug fix above) into `backtest()` -- currently inert since `BacktestResult` doesn't expose profit, but fixed for consistency before something later reads it.
- **False alarm, corrected rather than "fixed":** expected "Pastries" to fuzzy-match "Pastry Box," but it scores 0.556 on `SequenceMatcher`, just under the deliberately strict 0.6 cutoff -- correctly asks for clarification instead of guessing. Not a bug; a bad example in my own test suggestions.
- Verified: 132 backend tests pass (4 new: positive-slope guard, shared `period_sort_key` chronological + unparseable-fallback cases).
